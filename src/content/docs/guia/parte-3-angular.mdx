## 3.1 Conceptos básicos de Angular

A diferencia de Vue, un componente Angular es una **clase de TypeScript** decorada con
`@Component`, con su plantilla normalmente en un archivo aparte:

```ts title="ejemplo de juguete — no forma parte del proyecto"
import { Component } from '@angular/core';

@Component({
  selector: 'app-ejemplo',
  standalone: true,
  templateUrl: './ejemplo.component.html',
})
export class EjemploComponent {
  contador = 0; // propiedad normal de la clase — no necesita "ref"
}
```

```html title="ejemplo.component.html"
<button (click)="contador = contador + 1">{{ contador }}</button>
```

:::note[💡 Concepto: detección de cambios]
En Vue envuelves un valor con `ref()` para hacerlo reactivo. En Angular, una propiedad normal
de la clase ya es "observable" por el framework: Angular corre su propio ciclo de **detección
de cambios** después de eventos (clicks, respuestas HTTP) y vuelve a evaluar la plantilla.
:::

## 3.5 Reemplaza el array fijo por una llamada real a la API

Con el backend de la [Parte 1](/guia/parte-1-backend/) corriendo, primero habilita
`HttpClient`:

```ts title="src/app/app.config.ts"
import { ApplicationConfig, provideZoneChangeDetection } from '@angular/core';
import { provideHttpClient } from '@angular/common/http'; // habilita el servicio HttpClient en toda la app

export const appConfig: ApplicationConfig = {
  // "providers": la lista de servicios disponibles para inyección de dependencias en toda la app;
  // sin provideHttpClient() aquí, inyectar HttpClient en cualquier servicio fallaría en tiempo de ejecución
  providers: [provideZoneChangeDetection({ eventCoalescing: true }), provideHttpClient()]
};
```

:::note[💡 Concepto: `HttpClient` devuelve Observables, no Promesas]
RxJS (la librería detrás de `HttpClient`) modela peticiones asíncronas como **Observables**:
algo a lo que te "suscribes" y que puede emitir varios valores en el tiempo (útil para
WebSockets, por ejemplo). Para una petición HTTP normal solo te interesa el primer valor que
emite, así que `firstValueFrom(observable)` lo convierte en una Promesa común — y así puedes
seguir escribiendo `async/await`, igual que en la versión Vue.
:::

Los tipos:

```ts title="src/app/models/pedido.ts"
export interface Cliente {
  nombre: string;
  email: string;
}

export interface Pedido {
  id?: number | null;
  fecha: string;
  total: number;
  cliente: Cliente;
}
```

El servicio:

```ts title="src/app/services/pedido.service.ts"
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { firstValueFrom } from 'rxjs'; // convierte un Observable en una Promesa (ver el aside de arriba)
import type { Pedido } from '../models/pedido';

const API_URL = 'http://localhost:5000/api/pedidos';

@Injectable({ providedIn: 'root' }) // "providedIn: 'root'": una única instancia compartida por toda la app
export class PedidoService {
  // "private http: HttpClient" en el constructor es a la vez el parámetro Y la propiedad de la clase
  // (azúcar sintáctico de TypeScript); Angular inyecta automáticamente la instancia de HttpClient aquí
  constructor(private http: HttpClient) {}

  obtenerTodos(): Promise<Pedido[]> {
    // this.http.get<Pedido[]>(...) devuelve un Observable; firstValueFrom espera su primer valor y lo entrega como Promise
    return firstValueFrom(this.http.get<Pedido[]>(API_URL));
  }
}
```

Y en el componente, reemplaza el array fijo:

```ts title="src/app/app.component.ts"
import { Component, OnInit } from '@angular/core'; // OnInit: interfaz que exige implementar ngOnInit()
import { CommonModule } from '@angular/common';
import { PedidoService } from './services/pedido.service';
import type { Pedido } from './models/pedido';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [CommonModule],
  templateUrl: './app.component.html',
})
export class AppComponent implements OnInit { // "implements OnInit": promesa al compilador de que existe ngOnInit()
  pedidos: Pedido[] = [];

  constructor(private pedidoService: PedidoService) {} // Angular inyecta la única instancia compartida del servicio

  // ngOnInit: hook de ciclo de vida que Angular llama una vez, cuando el componente ya está listo
  // (equivalente a onMounted en Vue) — mejor lugar para disparar la carga inicial de datos
  async ngOnInit() {
    this.pedidos = await this.pedidoService.obtenerTodos();
    console.log('Pedidos recibidos del backend:', this.pedidos);
  }
}
```

```html title="src/app/app.component.html (agrega el *ngIf de vacío)"
<div *ngIf="pedidos.length === 0" class="p-6 text-center text-gray-500">
  No hay pedidos registrados.
</div>
<table *ngIf="pedidos.length > 0" class="w-full text-left">
  <!-- ... el resto de la tabla, igual que antes ... -->
</table>
```

## 3.6 Cómo hablan dos componentes: `@Input` y `@Output`

Hasta ahora todo vive en un único componente, `AppComponent`. Eso no escala: en la Parte 3 de
Vue ya separaste el formulario y la tabla en sus propios archivos, y en Angular vas a hacer lo
mismo. Pero antes de tocar el proyecto real, entendamos el mecanismo con un ejemplo
completamente aislado.

Imagina un componente hijo que saluda a alguien, y avisa a su padre cada vez que lo hace:

```ts title="src/app/saludo/saludo.component.ts — EJEMPLO DE JUGUETE, no forma parte del CRUD"
import { Component, EventEmitter, Input, Output } from '@angular/core';

@Component({
  selector: 'app-saludo', // el tag que usarás en el HTML del padre: <app-saludo>
  standalone: true,
  templateUrl: './saludo.component.html',
})
export class SaludoComponent {
  @Input() nombre = ''; // el padre puede escribir este valor desde afuera; '' es el valor por defecto
  @Output() saludado = new EventEmitter<string>(); // canal de eventos que el padre puede escuchar

  saludar() {
    this.saludado.emit(this.nombre); // dispara el evento "saludado", mandando el nombre como dato
  }
}
```

```html title="src/app/saludo/saludo.component.html"
<p>Hola, {{ nombre }}</p>
<button (click)="saludar()">Saludar</button>
```

Y lo usas desde el padre así:

```ts title="src/app/app.component.ts (solo para este experimento)"
import { Component } from '@angular/core';
import { SaludoComponent } from './saludo/saludo.component'; // hay que importar el componente hijo para poder usarlo

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [SaludoComponent], // declara qué componentes hijos puede usar la plantilla de este componente
  templateUrl: './app.component.html',
})
export class AppComponent {
  ultimoSaludo = '';

  // este método lo llama el HIJO (vía el evento "saludado"), no un click directo en este componente
  registrarSaludo(nombre: string) {
    this.ultimoSaludo = nombre;
    console.log('El hijo avisó que saludó a:', nombre);
  }
}
```

```html title="src/app/app.component.html (solo para este experimento)"
<!-- "nombre=" pasa un valor fijo (@Input); "(saludado)=" escucha el evento (@Output), $event trae lo que se emitió -->
<app-saludo nombre="Ana" (saludado)="registrarSaludo($event)"></app-saludo>
<p>Último saludo recibido en el padre: {{ ultimoSaludo }}</p>
```

:::tip[📝 Haz esto ahora — pruébalo en un proyecto aparte o temporalmente en el tuyo]
Crea estos dos archivos, ajusta `AppComponent` temporalmente como arriba, corre la app, y
presiona "Saludar". Abre la consola.
:::

```text title="✅ resultado real en la consola"
El hijo avisó que saludó a: Ana
```

:::note[💡 Concepto: props hacia abajo, eventos hacia arriba]
`@Input() nombre` es cómo el **padre le pasa datos al hijo** — en la plantilla del padre,
`nombre="Ana"` (o `[nombre]="variable"` si es dinámico). `@Output() saludado` es cómo el
**hijo le avisa algo al padre** sin modificarlo directamente — declara un `EventEmitter`, lo
`emit()` cuando pasa algo, y el padre lo escucha con `(saludado)="metodo($event)"`. Es
exactamente el mismo patrón que ya usaste en Vue con `defineProps`/`defineEmits`: datos hacia
abajo, eventos hacia arriba. El nombre cambia, el diseño no.
:::

### Aplica el mismo patrón: extrae el formulario

Ahora que viste el mecanismo aislado, vas a crear `PedidoFormComponent` usando exactamente la
misma idea: el hijo no sabe nada de HTTP ni del backend — solo junta los datos del formulario y
avisa al padre con `@Output() guardar`.

```ts title="src/app/components/pedido-form/pedido-form.component.ts"
import { Component, EventEmitter, Output } from '@angular/core';
import { CommonModule } from '@angular/common';
import { FormsModule } from '@angular/forms'; // trae ngModel, necesario para [(ngModel)] en la plantilla
import type { Pedido } from '../../models/pedido';

@Component({
  selector: 'app-pedido-form',
  standalone: true,
  imports: [CommonModule, FormsModule],
  templateUrl: './pedido-form.component.html',
})
export class PedidoFormComponent {
  @Output() guardar = new EventEmitter<Pedido>(); // este componente no sabe nada de HTTP: solo avisa "aquí hay un pedido"

  // estado inicial del formulario — igual que en Vue, con valores por defecto razonables
  formulario: Pedido = {
    fecha: new Date().toISOString().slice(0, 16),
    total: 0,
    cliente: { nombre: '', email: '' },
  };

  submit() {
    this.guardar.emit({ ...this.formulario }); // copia superficial, para no compartir la misma referencia con el padre
  }
}
```

```html title="src/app/components/pedido-form/pedido-form.component.html"
<!-- (ngSubmit) reemplaza el envío normal del form; evita el recargo de página que haría el navegador por defecto -->
<form (ngSubmit)="submit()" class="bg-white shadow-md rounded-lg p-6 mb-6 border border-gray-200">
  <h2 class="text-xl font-bold text-gray-800 mb-4">Registrar Nuevo Pedido</h2>
  <div class="grid grid-cols-2 gap-4 mb-4">
    <!-- [(ngModel)] es two-way binding: lee Y escribe formulario.cliente.nombre; "name" es obligatorio (ver nota abajo) -->
    <input [(ngModel)]="formulario.cliente.nombre" name="nombre" placeholder="Nombre del cliente" required class="border rounded px-3 py-2" />
    <input [(ngModel)]="formulario.cliente.email" name="email" type="email" placeholder="Email" required class="border rounded px-3 py-2" />
    <input [(ngModel)]="formulario.fecha" name="fecha" type="datetime-local" required class="border rounded px-3 py-2" />
    <input [(ngModel)]="formulario.total" name="total" type="number" step="0.01" required class="border rounded px-3 py-2" />
  </div>
  <button type="submit" class="bg-indigo-600 text-white px-4 py-2 rounded font-medium">Guardar Pedido</button>
</form>
```

:::caution[⚠️ Nota: cada campo con `ngModel` necesita `name`]
A diferencia de `v-model`, Angular exige un atributo `name` único por cada input dentro de un
`<form>` con `ngModel` — lo usa internamente para registrar el control. Olvidarlo es uno de los
errores más comunes al empezar con formularios en Angular.
:::

Agrega el método `crear` al servicio, e importa/usa `PedidoFormComponent` desde `AppComponent`:

```ts title="src/app/services/pedido.service.ts (agregar dentro de la clase)"
crear(pedido: Pedido): Promise<Pedido> {
  return firstValueFrom(this.http.post<Pedido>(API_URL, pedido));
}
```

```ts title="src/app/app.component.ts (reemplaza todo el archivo)"
import { Component, OnInit } from '@angular/core';
import { CommonModule } from '@angular/common';
import { PedidoService } from './services/pedido.service';
import { PedidoFormComponent } from './components/pedido-form/pedido-form.component';
import type { Pedido } from './models/pedido';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [CommonModule, PedidoFormComponent], // ahora AppComponent puede usar <app-pedido-form> en su plantilla
  templateUrl: './app.component.html',
})
export class AppComponent implements OnInit {
  pedidos: Pedido[] = [];

  constructor(private pedidoService: PedidoService) {}

  async ngOnInit() {
    await this.cargarPedidos();
  }

  async cargarPedidos() {
    this.pedidos = await this.pedidoService.obtenerTodos();
  }

  // recibe el pedido que PedidoFormComponent emitió por su @Output "guardar"
  async guardarPedido(pedido: Pedido) {
    await this.pedidoService.crear(pedido);
    await this.cargarPedidos(); // refresca la tabla para reflejar el pedido recién creado
  }
}
```

```html title="src/app/app.component.html (agrega app-pedido-form arriba de la tabla)"
<!-- "(guardar)=" escucha el @Output del hijo; $event trae el Pedido que el hijo emitió -->
<app-pedido-form (guardar)="guardarPedido($event)"></app-pedido-form>
```

## 3.7 Precargar datos en un hijo: `ngOnChanges`

Falta el modo edición: cuando el usuario presiona "Editar" en una fila, el mismo formulario
debe precargarse con los datos de ese pedido. El padre va a cambiar el valor de un `@Input` del
hijo — y el hijo necesita *enterarse* de ese cambio para actualizar su propio estado interno.
Otra vez, primero el mecanismo aislado:

```ts title="src/app/contador-hijo/contador-hijo.component.ts — EJEMPLO DE JUGUETE"
import { Component, Input, OnChanges } from '@angular/core'; // OnChanges: interfaz que exige implementar ngOnChanges()

@Component({
  selector: 'app-contador-hijo',
  standalone: true,
  templateUrl: './contador-hijo.component.html',
})
export class ContadorHijoComponent implements OnChanges {
  @Input() valorPadre = 0;

  // Angular llama este método automáticamente cada vez que valorPadre cambia de valor
  ngOnChanges() {
    console.log('El padre cambió valorPadre a:', this.valorPadre);
  }
}
```

```html title="src/app/contador-hijo/contador-hijo.component.html"
<p>El hijo recibió: {{ valorPadre }}</p>
```

```html title="app.component.html (solo para este experimento)"
<!-- cada click reasigna "valor" en el padre -> Angular detecta el cambio -> se lo pasa al hijo por [valorPadre] -->
<button (click)="valor = valor + 1">Incrementar</button>
<app-contador-hijo [valorPadre]="valor"></app-contador-hijo>
```

:::tip[📝 Haz esto ahora]
Agrega una propiedad `valor = 0` al `AppComponent` de este experimento, corre la app, y
presiona "Incrementar" dos veces.
:::

```text title="✅ resultado real en la consola — se ejecuta también al iniciar, y una vez por cada click"
El padre cambió valorPadre a: 0
El padre cambió valorPadre a: 1
El padre cambió valorPadre a: 2
```

:::note[💡 Concepto: `ngOnChanges` — el "watch" de Angular]
`ngOnChanges` es un **hook de ciclo de vida**: un método que Angular llama automáticamente en
momentos específicos de la vida de un componente. Se ejecuta cada vez que cambia el valor de
cualquier `@Input`, **incluyendo la primera vez que el componente recibe ese valor** — por eso
ves el log con `0` apenas arranca, sin haber hecho click todavía. Es el equivalente directo del
`watch(..., { immediate: true })` que usaste en Vue.
:::

### Aplica el patrón: modo edición en `PedidoFormComponent`

```ts title="src/app/components/pedido-form/pedido-form.component.ts (reemplaza todo el archivo)"
import { Component, EventEmitter, Input, Output, OnChanges } from '@angular/core';
import { CommonModule } from '@angular/common';
import { FormsModule } from '@angular/forms';
import type { Pedido } from '../../models/pedido';

// función (no un valor fijo) para poder generar un formulario "vacío" nuevo cada vez que se necesite
const vacio = (): Pedido => ({
  fecha: new Date().toISOString().slice(0, 16),
  total: 0,
  cliente: { nombre: '', email: '' },
});

@Component({
  selector: 'app-pedido-form',
  standalone: true,
  imports: [CommonModule, FormsModule],
  templateUrl: './pedido-form.component.html',
})
export class PedidoFormComponent implements OnChanges {
  @Input() pedidoAEditar: Pedido | null = null; // null = modo crear; con datos = modo editar
  @Output() guardar = new EventEmitter<Pedido>();
  @Output() cancelar = new EventEmitter<void>(); // <void>: este evento no manda ningún dato, solo avisa "cancelé"

  formulario: Pedido = vacio();

  // se dispara cada vez que pedidoAEditar cambia (incluida la primera vez que llega un valor)
  ngOnChanges() {
    this.formulario = this.pedidoAEditar
      ? { ...this.pedidoAEditar, cliente: { ...this.pedidoAEditar.cliente } } // copia los datos del pedido a editar
      : vacio(); // o resetea, si el padre volvió a poner null
  }

  submit() {
    this.guardar.emit({ ...this.formulario });
  }

  onCancelar() {
    this.formulario = vacio(); // limpia también el propio estado interno, no solo avisa al padre
    this.cancelar.emit();
  }
}
```

```html title="src/app/components/pedido-form/pedido-form.component.html (reemplaza todo el archivo)"
<form (ngSubmit)="submit()" class="bg-white shadow-md rounded-lg p-6 mb-6 border border-gray-200">
  <h2 class="text-xl font-bold text-gray-800 mb-4">
    {{ formulario.id ? '✏️ Editar Pedido' : '➕ Registrar Nuevo Pedido' }}
  </h2>
  <div class="grid grid-cols-2 gap-4 mb-4">
```

```ts title="src/app/app.component.ts (reemplaza todo el archivo)"
import { PedidoService } from './services/pedido.service';
import { PedidoFormComponent } from './components/pedido-form/pedido-form.component';
import { PedidoTablaComponent } from './components/pedido-tabla/pedido-tabla.component';
import type { Pedido } from './models/pedido';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [PedidoFormComponent, PedidoTablaComponent], // ya no importa CommonModule: no queda *ngIf/*ngFor en ESTE archivo
  templateUrl: './app.component.html',
})
export class AppComponent implements OnInit {
  pedidos: Pedido[] = []; // el estado "fuente de verdad", que baja a ambos hijos por @Input
  pedidoSeleccionado: Pedido | null = null; // null = modo crear; con datos = modo editar

  constructor(private pedidoService: PedidoService) {}

  ngOnInit() {
    this.cargarPedidos();
  }

  async cargarPedidos() {
    this.pedidos = await this.pedidoService.obtenerTodos();
  }

  // recibe el pedido emitido por (guardar) desde PedidoFormComponent
  async guardarPedido(pedido: Pedido) {
    // misma decisión que en el backend (Parte 1) y en Vue: con id -> actualizar, sin id -> crear
    if (pedido.id) {
      await this.pedidoService.actualizar(pedido.id, pedido);
    } else {
      await this.pedidoService.crear(pedido);
    }
    this.pedidoSeleccionado = null; // vuelve a modo crear
    await this.cargarPedidos();
  }

  // recibe el id emitido por (eliminar) desde PedidoTablaComponent
  async borrarPedido(id: number) {
    if (confirm(`¿Eliminar el pedido #${id}?`)) {
      await this.pedidoService.eliminar(id);
      await this.cargarPedidos();
    }
  }
}
```

## 3.8 Angular moderno: Signals

Todo lo anterior (`@Input`, `@Output`, `ngOnChanges`) es el Angular "clásico", vigente desde
hace años y el que vas a encontrar en la mayoría de proyectos existentes. Desde Angular 17, el
framework ofrece un modelo de reactividad nuevo llamado **Signals** — y desde Angular 19 es
estable y recomendado para proyectos nuevos. Vale la pena conocerlo, así que vamos a probarlo
igual que todo lo demás: con ejemplos aislados primero.

:::note[💡 Concepto: ¿qué es una signal?]
Una `signal` es un contenedor de un valor que **sabe quién la está leyendo**, y cuando cambia,
notifica automáticamente solo a esas partes exactas de la plantilla — sin que Angular tenga que
revisar todo el árbol de componentes en busca de cambios, como hace con la detección de
cambios clásica. Si te suena parecido al `ref()` de Vue que usaste en la Parte 3 (Vue), es
porque es exactamente la misma idea: reactividad explícita y de grano fino, en vez de "vigilar
propiedades de una clase" por detrás.
:::

### Signal y computed

```ts title="src/app/contador-signal/contador-signal.component.ts — EJEMPLO DE JUGUETE"
import { Component, signal, computed } from '@angular/core';

@Component({
  selector: 'app-contador-signal',
  standalone: true,
  templateUrl: './contador-signal.component.html',
})
export class ContadorSignalComponent {
  contador = signal(0); // crea una signal con valor inicial 0 (no es un number normal, es un contenedor reactivo)
  doble = computed(() => this.contador() * 2); // signal derivada: se recalcula sola cuando "contador" cambia

  incrementar() {
    // .update() recibe el valor ACTUAL y devuelve el nuevo; nunca se reasigna "this.contador = ..." directamente
    this.contador.update((valorActual) => valorActual + 1);
  }
}
```

```html title="src/app/contador-signal/contador-signal.component.html"
<!-- "contador()" con paréntesis: así se LEE una signal en la plantilla, igual que en el .ts -->
<p>Contador: {{ contador() }}</p>
<p>Doble: {{ doble() }}</p>
<button (click)="incrementar()">+1</button>
```

:::


:::note[💡 Concepto: `signal()` se lee como función, `computed()` se recalcula solo]
A diferencia de una propiedad normal, para leer el valor de una signal la **llamas como
función**: `contador()`, no `contador`. Para cambiarla, nunca la reasignas directamente — usas
`.set(nuevoValor)` o `.update(valorActual => ...)`. Y `computed()` crea una signal derivada que
Angular recalcula automáticamente solo cuando `contador` cambia, sin que tengas que declarar de
qué depende — lo detecta solo, porque la función que le pasaste llamó a `contador()` por
dentro.
:::

### `input()` y `output()`: la versión signal de `@Input`/`@Output`

```ts title="src/app/saludo-signal/saludo-signal.component.ts — EJEMPLO DE JUGUETE"
import { Component, input, output } from '@angular/core'; // funciones en minúscula, no decoradores

@Component({
  selector: 'app-saludo-signal',
  standalone: true,
  templateUrl: './saludo-signal.component.html',
})
export class SaludoSignalComponent {
  nombre = input(''); // reemplaza @Input() nombre = ''; el valor entre paréntesis es el valor por defecto
  saludado = output<string>(); // reemplaza @Output() saludado = new EventEmitter<string>()

  saludar() {
    this.saludado.emit(this.nombre()); // "nombre()" para leerlo — output() se sigue usando con .emit() igual que antes
  }
}
```

```html title="src/app/saludo-signal/saludo-signal.component.html"
<p>Hola, {{ nombre() }}</p>
<button (click)="saludar()">Saludar</button>
```

Se usa exactamente igual que `SaludoComponent` de la sección 3.6 —
`<app-saludo-signal nombre="Carlos" (saludado)="..."></app-saludo-signal>` — el padre no nota
ninguna diferencia. Lo único que cambió es cómo está escrito el hijo por dentro: funciones en
vez de decoradores, sin necesidad de `ngOnChanges` porque `nombre()` ya es reactivo por sí
mismo.

### `@if` / `@for`: el nuevo control de flujo en plantillas

Angular 17 también reemplazó `*ngIf`/`*ngFor` por una sintaxis nueva, sin necesitar
`CommonModule`:

```ts title="src/app/lista-signal/lista-signal.component.ts — EJEMPLO DE JUGUETE"
import { Component, signal } from '@angular/core';

@Component({
  selector: 'app-lista-signal',
  standalone: true,
  templateUrl: './lista-signal.component.html',
})
export class ListaSignalComponent {
  items = signal<string[]>([]); // signal que guarda un array; <string[]> porque empieza vacío y TypeScript no puede inferirlo

  agregar() {
    // "[...actual, nuevo]" crea un array NUEVO con todo lo anterior más el elemento agregado;
    // nunca se hace actual.push(...) directamente — las signals detectan el cambio comparando la referencia
    this.items.update((actual) => [...actual, `item ${actual.length + 1}`]);
  }
}
```

```html title="src/app/lista-signal/lista-signal.component.html"
<!-- @if/@else: reemplaza *ngIf/*ngElse, sin necesitar CommonModule -->
@if (items().length === 0) {
  <p>No hay items todavía.</p>
} @else {
  <ul>
    <!-- @for exige "track": aquí, el propio string (cada item ya es único) -->
    @for (item of items(); track item) {
      <li>{{ item }}</li>
    }
  </ul>
}
<button (click)="agregar()">Agregar</button>
```

:::caution[⚠️ Nota: el signo `@` ahora es sintaxis reservada]
Desde que existe `@if`/`@for`, escribir un `@` suelto en cualquier otro lugar de una plantilla
Angular (por ejemplo, en un texto como "contacto@empresa.com") puede confundir al compilador. Si
necesitas mostrar un `@` literal, escríbelo como `&#64;`.
:::

:::note[💡 Concepto: `track` en `@for` es obligatorio]
A diferencia de `*ngFor` (donde `trackBy` era opcional), `@for` te obliga a especificar por qué
campo identificar cada elemento — aquí, `track item` porque son strings simples; en un array de
objetos usarías `track item.id`. Es el mismo problema que resuelve `:key` en `v-for` de Vue:
ayudar a Angular a saber qué elemento del DOM corresponde a cuál dato cuando la lista cambia.
:::
